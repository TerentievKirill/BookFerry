# Архитектура BookFerry Server

## Структура проекта

```text
bookferry/
│
├── main.py              # Точка входа
├── requirements.txt     # Зависимости
├── .env                 # Настройки
├── README.md
│
└── app/
    ├── api.py           # HTTP API
    ├── models.py        # Pydantic модели
    ├── config.py        # Загрузка настроек
    └── services/
        ├── mail.py
        ├── opds.py
        └── telegram.py
```

---

# main.py

## Назначение

Точка входа в приложение.

Практически не содержит бизнес-логики.

```python
from fastapi import FastAPI
from app.api import router

app = FastAPI()

app.include_router(router)
```

Основная задача:

- создать FastAPI;
- подключить роуты;
- в будущем подключить middleware, логирование и т.д.

---

# api.py

## Назначение

Здесь находятся **все HTTP-ручки**.

Например:

```text
GET  /health
POST /search
POST /send-book
```

Каждая ручка должна:

1. принять запрос;
2. проверить входные данные;
3. вызвать нужный сервис;
4. вернуть ответ.

### ❌ Не должна

- скачивать книги;
- отправлять почту;
- работать с Telegram;
- содержать сложную бизнес-логику.

---

# models.py

Описание моделей запросов и ответов.

Например:

```python
class SearchRequest(BaseModel):
    query: str
```

или

```python
class SendBookRequest(BaseModel):
    email: str
    book: Book
```

FastAPI автоматически проверяет входящий JSON.

---

# config.py

Читает настройки из `.env`.

Например:

```text
BOT_TOKEN=...
SMTP_HOST=...
SMTP_LOGIN=...
SMTP_PASSWORD=...
```

Все остальные модули получают настройки отсюда.

## telegram.py

# Главное правило

Если поймал себя на мысли:

> "Сейчас прямо в api.py скачаю книгу..."

значит архитектура уже нарушается.

Правильно:

```text
api.py
    │
    ▼
book_delivery.deliver_book(...)
```

---

# Пример

## ❌ Плохо

```python
@router.post("/search")
def search():

    requests.get(...)

    xml = ...

    send_email(...)
```

---

## ✅ Хорошо

```python
@router.post("/search")
def search(request):

    return flibusta.search(request.title)
```

Вся логика находится внутри `services/flibusta.py`.

---

# Когда меняется main.py

Очень редко.

Обычно только при добавлении:

- middleware;
- логирования;
- CORS;
- авторизации;
- подключения базы данных.

В 95% случаев работа идет в `api.py` и `services/`.

---

# Простое правило

| Если нужно... | Пишем в... |
|---------------|------------|
| Создать новую HTTP-ручку | `api.py` |
| Описать входной JSON | `models.py` |
| Прочитать настройки | `config.py` |
| Отправить письмо | `services/mail.py` |
| Скачать книгу | `services/flibusta.py` |
| Работать с Telegram | `services/telegram.py` |
| Настроить FastAPI | `main.py` |

# Идея архитектуры

```text
API
 │
 ▼
Services
 │
 ▼
Внешние сервисы
```

API ничего не знает о том, **как** скачиваются книги или отправляются письма.

Он только принимает запрос и вызывает нужный сервис.

# Текущий API

## GET /health

Проверка работоспособности сервиса.

Ответ:

```json
{
  "status": "ok"
}
```

---

## POST /search

Запрос:

```json
{
  "query": "Лабиринт отражений"
}
```

Ответ:

```json
[
  {
    "author": "Лукьяненко Сергей",
    "title": "Лабиринт отражений",
    "url": "https://flibusta.is/b/111094/epub"
  }
]
```

---

## POST /send-book

Запрос:

```json
{
  "email": "user@example.com",
  "book": {
    "author": "Лукьяненко Сергей",
    "title": "Лабиринт отражений",
    "url": "https://flibusta.is/b/111094/epub"
  }
}
```

Поток выполнения:

Book -> download.py -> mail.py -> PocketBook
